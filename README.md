# assay

[![tests](https://github.com/zacktiger/assay/actions/workflows/tests.yml/badge.svg)](https://github.com/zacktiger/assay/actions/workflows/tests.yml)

A small investing API with an LLM-backed explanation layer, built as the system
under test for an automated QA suite. **The QA system is the project**; the
application exists to be tested, and to be broken.

The interesting problem here is the LLM endpoint. A projection is either
arithmetically correct or it isn't — that is ordinary testing. But an
explanation generated by a language model has no expected value to assert
against, so the suite tests it the only way that works: by pinning down what it
must never do, and checking every response against figures the application
computed itself.

```

```

**Live:** [assay-api-mw3v.onrender.com/docs](https://assay-api-mw3v.onrender.com/docs)
— the OpenAPI page is the demo surface; every bound it publishes is one the
boundary tests pin down. Free tier, so the first request after fifteen idle
minutes pays a cold start.

## In plain words

**What this is.** A small investing API (sign up, deposit money, ask for a
recommendation) plus 274 automated tests that try to break it. The tests are
the project. The API is there to give them something real to test.

**How it's built.** A request goes through four steps:

1. **Check the input.** FastAPI rejects anything outside the rules, such as an
   investment below ₹1,000 or above ₹1,00,000, with a `422` that names the
   field. The rules are written once, in `app/config.py`.
2. **Do the maths.** `app/finance.py` computes every number using exact
   decimals, never floats, so money never picks up rounding errors.
3. **Explain it.** The AI model gets the finished numbers and only puts them
   into words. It never calculates anything.
4. **Check the explanation.** `app/llm/guardrails.py` compares every number in
   the AI's answer with the real ones. An answer that invents a number, promises
   a guaranteed return, or leaks the model's hidden instructions is thrown away
   and replaced with safe pre-written text.

Data goes to SQLite when running locally and to Postgres in the live
deployment.

**How the testing works.** It's plain `pytest`. One command runs all 274
tests in about a minute, with no internet and no API key. The real AI model is
swapped for a predictable fake (`StubProvider` in `app/llm/stub.py`) that
always gives the same answer to the same input, which is what makes an AI
feature testable at all. For the AI tests, a second fake (`ScriptedProvider`)
feeds the checker deliberately bad answers, such as a made-up return rate or a
leaked prompt, and the test confirms each one gets caught.

Tests are tagged by what they check, so one group can run on its own
(`pytest -m boundary`, `pytest -m security`, and so on). GitHub Actions runs
the full suite on every push; that's the badge at the top.

**What the tests found.** Three real bugs, all fixed, each with a test that
keeps it fixed. The worst one made every out-of-range amount crash with a
`500` instead of returning "invalid input" (`422`). The tests also turned up
one limitation that was deliberately left in place, and two cases where the
test turned out to be wrong and the app was right. All six are written up in
[`docs/BUGS.md`](docs/BUGS.md).

## Running it

```bash
pip install -r requirements.txt

pytest                          # everything, ~49s
pytest -m boundary              # one category
pytest -m deployment            # deployment-surface checks
pytest -m "llm and not slow"    # combine markers
pytest tests/test_boundaries.py::test_investment_amount_boundaries  # one test
pytest -q --cov=app --cov-report=term-missing                       # coverage (93%)

uvicorn app.main:app --reload   # run the API, docs at /docs
```

The suite needs no API key and makes no network calls. It runs against a
deterministic stub provider, which is what makes the consistency test
meaningful — see [Testing the LLM](#testing-the-llm) below.

To run against live Claude instead, set `LLM_PROVIDER=anthropic` and
`ANTHROPIC_API_KEY` (see `.env.example`). To drive a deployed instance over
real HTTP rather than in-process, use `qa/api_client.py`.

## Architecture

```
       POST /recommendation
                │
                ▼
     ┌──────────────────────┐
     │  FastAPI + Pydantic  │  bounds enforced once, from app/config.py
     └──────────┬───────────┘
                │
                ▼
     ┌──────────────────────┐
     │    app/finance.py    │  ALL arithmetic, in Decimal
     └──────────┬───────────┘
                │  computed figures
                ▼
     ┌──────────────────────┐
     │     LLM provider     │  explains the figures; never computes them
     └──────────┬───────────┘
                │  untrusted text
                ▼
     ┌──────────────────────┐
     │  app/llm/guardrails  │  validates against the computed figures
     └──────────┬───────────┘
                │
        pass ───┴─── fail → deterministic fallback text
```

The split is the whole design. **The model never does arithmetic.** It is handed
finished numbers and asked only to put words around them, which means its output
can be checked against something objective. A test asserts this directly:
`test_model_is_never_asked_to_do_the_arithmetic` inspects the prompt and fails
if it contains "calculate" or "compute".

Money is `Decimal` end to end, `NUMERIC(18,2)` in the database, and rounded
half-up rather than banker's-rounded so that ledger totals agree with the sum of
their rows.

```
app/
  config.py       business bounds — the single source both the validator
                  and the boundary test data read from
  finance.py      deterministic projection maths
  security.py     PBKDF2 hashing, hashed bearer tokens
  llm/
    guardrails.py output validation — the safety-critical module
    prompts.py    system prompts, including the leak canary
    stub.py       deterministic provider + scripted test double
tests/            the suite
qa/
  test_data.py    boundary ladders and hostile strings, as data
  eval_dataset.csv  LLM evaluation cases
  api_client.py   HTTP client for testing a deployed instance
```

## Testing the LLM

Four properties, none of which require asserting on exact model text.

**It must not invent numbers.** The guardrail extracts every percentage from a
response and compares it against the set of figures the application actually
supplied. Anything else is a hallucination by construction — no judgement call:

```python
scripted_llm.responses = ["This will return 30% a year, easily."]
body = recommend(client, headers, asset_type="equity_index").json()

assert "30%" not in body["explanation"]      # suppressed
assert body["model"].endswith("+fallback")   # and the substitution is visible
```

**It must not promise certainty.** Nine phrasings of guaranteed/assured/risk-free
are checked, with the false-positive limitation documented in `KNOWN-001` rather
than papered over.

**It must not leak its instructions.** The system prompt contains a fixed canary
string, `INTERNAL-POLICY-7731`. If it ever appears in a response the prompt
leaked — a precise signal instead of a fuzzy judgement. Five prompt-injection
payloads are run against it.

**It must answer consistently.** The same question five times must produce one
answer, not five.

The guardrail is tested directly as well as through the endpoint, because it is
the component standing between a bad generation and the user.

The scripted provider is what makes this tractable: rather than waiting for a
real model to hallucinate, the test *hands* the endpoint the output a model
occasionally produces and asserts the guardrail catches it.

## Test design notes

**Boundaries are probed at four points.** For the 1,000–100,000 investment rule:
the bound itself, one paisa either side, one rupee either side, and the obvious
wrong answers (0, negative, null). One paisa matters because `999.99` and
`1000.00` are adjacent representable values in a two-decimal money type — that
is where an off-by-one actually lives.

**Malformed input is checked for coercion, not just rejection.** The risk is not
a crash; it is `True` silently becoming `1`, `""` becoming `0`, or `"50,000"`
parsing as `50`. Each of those returns 201 while writing a wrong number into a
financial record. Twelve malformed amounts assert 422.

**Integrity checks query the database in SQL, not through the API.** The
functional suite asks whether the API answered correctly; the integrity suite
asks whether the answer matches what was persisted, and whether
`balance == SUM(deposits) - SUM(withdrawals)` holds independently. A system can
pass every endpoint test and still have a balance that disagrees with its own
ledger.

**Bounds live in one place.** `app/config.py` defines them; the Pydantic
validator and `qa/test_data.py` both read from it. A test cannot drift from the
rule it is testing.

## Deploying it

Running at
[assay-api-mw3v.onrender.com](https://assay-api-mw3v.onrender.com/docs) on
Render's free tier — Docker, one worker, managed Postgres, schema created by
`scripts.init_db` as an ordered release step before the server binds. The
blueprint is [`render.yaml`](render.yaml).

```bash
docker compose up --build        # API + Postgres, schema created by the migrate step
curl localhost:8000/health/ready # {"status":"ready","database":"up"}
```

`ENVIRONMENT=production` flips two defaults: schema auto-creation off (a
`create_all` race across workers) and the OpenAPI docs off. Everything else is
identical between environments.

The deployment surface is tested, not just written — 37 cases covering probes,
security headers, paging caps, token revocation, the login throttle, and the
environment gating itself. The schema bootstrap is tested for idempotency and
for failing loudly on an unreachable database, because a deploy should stop
there rather than start a broken API.

Full runbook, configuration table and known gaps: [`docs/DEPLOY.md`](docs/DEPLOY.md).

**One constraint worth stating up front:** the login throttle is in-process, so
the container defaults to a single worker. Before scaling out, move rate
limiting to the gateway. The reasoning is in the runbook rather than buried in
a comment.

## What is deliberately not covered

- **Concurrency.** The lost-update path is *guarded* — the balance is re-read
  inside the transaction, with `SELECT … FOR UPDATE` on Postgres — but it is not
  *tested*, because the suite runs on SQLite where writes serialise at the file
  level and a race cannot be reproduced. The idempotency tests cover sequential
  retries only.
- **Live-model evaluation.** Every LLM test runs against the stub. That buys
  determinism and a free CI run; it does not tell you how the real model behaves.
  `AnthropicProvider` is written against the current SDK but has never made a
  real call. The guardrail is provider-independent and is the part that would
  hold.
- **Load and soak.** Response-time assertions here are per-request budgets
  (<500ms reads, <1.5s registration), not throughput measurements.
- **Frontend.** There isn't one; this is an API and its test suite.
- **Schema migrations.** `scripts/init_db.py` is create-only; altering a table
  against live data needs Alembic, which is not set up.
